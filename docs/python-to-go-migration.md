# Python v1 到 Go v2 的保留数据迁移方案

状态：实施设计，尚未实现专用迁移入口，也未执行生产迁移。本文适用于控制库 Schema 6、用量库 Schema 9 的 Python v1.1.5；更早版本必须另行识别真实结构，不能直接套用。目标版本应是完成演练的固定 Release 及其镜像摘要。

代码依据为编制时的工作区，其中存在并行维护的未提交修改；不将工作区行为直接视为已发布能力。实施前需在选定的干净 Release 上重新核对本文接口及全部门槛。

目标是让原有用户继续使用原 API Key、账号和额度，并能查询原用量历史。推荐采用“副本演练、一次维护切换、原路径接管”的方式。首次跨语言迁移完成后，才进入 [日常升级](upgrade.md) 流程。

## 1. 已确认的代码边界

| --- | --- | --- |

| 用量库 | Go Writer 严格要求 Schema 10，拒绝自动迁移；v1.1.5 源码使用 Schema 9 | [writer.go](../internal/usage/writer.go)、[schema.go](../internal/usage/schema.go)；历史源码 `v1.1.5:admin/usage_store.py` |
| 凭据 | 已有 AES-GCM、旧密码哈希和会话哈希兼容测试；这不能代替真实备份验证 | [控制库测试](../internal/controlplane/store_test.go)、[密码测试](../internal/portal/password_test.go)、[Portal Store 测试](../internal/usage/portal_store_test.go) |

不能直接在旧实例执行最新版一键安装命令。也不能先让 Go Admin 挂载生产数据“看看能否启动”：它可能修改控制库、配置文件和账号容器。

## 2. 必须保留的数据及核对方式

| 数据 | 保留要求 | 验收方式 |
| --- | --- | --- |
| 账号、路由、团队、成员关系 | ID、顺序、状态、关联不变；新增显示字段允许使用明确默认值 | 按稳定主键排序，对原有业务字段逐行计算摘要 |
| 外部 API Key | 所有记录及原字节保留，包含 active、revoked、rotated；不通过重新创建用户导入 | 比较 sequence、状态及秘密的受保护摘要；旧撤销 Key 仍拒绝 |
| 内部 Key、管理密钥 | 原字节和绑定关系保留，禁止自动补建掩盖缺失 | 全量摘要及缺失关联检查；启动前后再次比较 |
| 主密钥与加密秘密 | 两者同批备份，保留原 32 字节主密钥；秘密须全部解密并校验摘要成功 | 只报告成功/失败数量，不输出明文 |
| OAuth | 原账号目录、所有文件及权限保留 | 停止对应写入后的文件清单、大小和摘要；运行后允许正常刷新 Token |
| 用量历史 | 原 `id`、`event_key`、时间、用户/账号/团队归属和所有 Token 字段不变 | 事件数、最大 ID、分块行摘要、按用户/日/模型汇总；保留自增序列 |
| 额度 | 默认额度、个人额度、bonus、usage_reset、已用量及历史权重不变 | 按用户比较切换时剩余额度；跨周边界测试 |
| Portal | 密码哈希、must_change、凭据和会话记录保留 | 原密码能登录；会话 cookie 是否可沿用单独验收，不能承诺免重新登录 |
| 配置与派生文件 | 保存旧配置和快照；Go 派生文件从已核对的权威数据重新生成 | 逐字段比较新旧有效配置；路径/格式变化进入允许差异清单 |
| 回滚材料 | 旧镜像内容、Compose、环境投影、入口配置、启动方式、调度、账号挂载及 Caddy 证书数据 | 原版恢复演练，不以“备份文件存在”为完成 |

在线统计只用于估算。最终基线必须在停止新业务请求、排空请求和队列、停止所有相关写入之后采集；两份数据库的基线应属于同一个停写窗口。

保留所有原始历史记录。即使其账号或用户已被历史操作删除，也不能因当前关联检查失败而清理用量；应区分原有孤立历史与迁移新增错误。

## 3. 最小数据转换

### 控制库 6 → 7

在副本上使用与目标镜像一致的控制库迁移逻辑，保留既有账户、Key、团队、配置和加密内容。团队增加 `tag_style`。以原字段摘要证明没有顺带修改业务关系。

对于更早版本，先保留完整旧库；遇到 `gost_port` 或 `gost_tunnel_auth`，必须先解释其与实际有效代理配置的对应关系。未知字段或未知版本停止转换，不把删字段当作自动“清理”。外部 GOST/Xray 和独立 CPA 服务不在迁移操作范围内。

### 用量库 9 → 10

对已确认与 v1.1.5 结构匹配的副本，核心 DDL 是给 `user_quota_policies` 添加可空 `reset_at INTEGER`，原记录取 `NULL`。随后核对全部目标列、索引、约束和自增序列，最后才将 `PRAGMA user_version` 更新为 10。

整个转换应在事务内执行，失败回滚；二次执行必须验证“已完整迁移”后无操作。不能仅修改版本号，也不能重新导入全部事件或按新权重重算历史。

同时在转换后的控制库明确设置 `user_quota.reset_personal_weekly_on_new_week=false`，使旧的个人额度覆盖继续有效。若今后需要新周自动重置，应作为另一个业务变更启用。

保留原业务时区及 `usage_meta` 中的周统计标记。若目标 Release 改用统一时区字段，执行等价映射；不得在此次迁移中改变自然日/自然周边界。已有聚合正确时，不把全历史重建放入维护窗口。

### 账号配置和启动布局

保留实际业务根目录为最终 `$LEGACY_ROOT`，运维脚本和备份使用独立目录。演练目录 `$REHEARSAL_ROOT` 与正式数据完全分离，不搬迁生产根目录，也不以符号链接连接两者。

旧账号 `configs/<account>.yaml` 转为 `configs/<account>/config.yaml`。迁移记录每个容器的真实 Image ID、端口、网络、挂载、启动命令和 restart policy，逐个处理并探测。不能使用统一 `latest` 重建全部账号，因为各账号原本可能运行不同镜像。

保留旧文件的私有回滚副本：当前 Go 挂载迁移成功后会删除旧单文件。无论原容器此前运行还是停止，必须核对重建后的预期状态；停止容器不会获得与运行容器相同的自动探测覆盖。

对渲染结果做语义 diff，包括 API Key 列表、管理密钥、代理、重试、队列保留时间、会话亲和、日志和图片生成配置。默认值改变不等于兼容；无法解释的差异阻止切换。

## 4. 上线前需要实现的工具

以下是待实现能力，不是当前可执行命令。建议由一个迁移工具负责状态机，并通过现有 `scripts/run.sh` 衔接正式交付，不增加另一个长期部署入口。

| 能力 | 输入/输出 | 安全边界 |
| --- | --- | --- |
| inspect / plan | 旧版本、库结构、容器/挂载/入口清单 → 脱敏计划及允许差异 | 只读；不启动应用，不执行 LPOP，不输出秘密 |
| backup / verify-backup | 停写证据、原路径 → 两库、配对主密钥及完整恢复清单 | SQLite Backup API；文件清单和校验；不把在线 WAL/SHM 混入归档 |
| convert-copy / verify | 已验证备份 → Schema 7/10 的独立副本和逐项差异报告 | 源备份不可变；未知版本、符号链接、错误密钥或丢记录立即失败 |
| prepare / cutover | 固定发布包、转换副本、原部署身份 → 新运行状态 | 显式维护步骤；所有权确认；目标路径和服务清单精确匹配 |
| rollback / reconcile | 切换前基线、Go 新增数据、旧版清单 → 可继续运行的旧版本 | 区分写入前/后回滚；保留新增业务数据，禁止直接覆盖回旧快照 |

工具应有持久迁移记录，包含阶段、源/目标版本、备份摘要、水位、允许差异及已完成账号。中途断电重跑时先核对实际状态，不重复执行破坏性步骤；两库尚未同时发布完成时任何服务不得启动。

需要补齐的部署适配还包括：保留自定义运行根目录与项目身份、避免上层 `write_target_env` 覆盖旧配置，以及现有 Caddy 与 Go Edge 的持久入口网络配置。不能假定当前一键脚本已经提供这些能力。

## 5. 演练与正式切换

### A. 离线及隔离演练

1. 固定一个完整 Go Release、四组件摘要和迁移工具版本。用干净源码完成发布校验；由工作站发布，目标只拉取。
2. 取得一致性演练副本并验证恢复。在线 SQLite Backup API 能保证单库快照，但两库与 OAuth 的整体时间一致性需额外协调；在线初始副本不能替代最终停写备份。
3. 转换副本，核对原字段、秘密解密、Key 状态、用量及剩余额度。测量真实数据量下的转换、校验和恢复耗时。
4. 演练环境使用独立 Docker daemon/测试环境、Compose 项目、网络和端口；禁止挂载生产 Docker Socket、消费生产队列或启动真实 OAuth 副本。Admin 的 `--runtime-read-only` 仅限制 Docker 操作，不代表整个应用不会写数据库。
5. 用脱敏 fixture 或专用测试账号验证 Admin、Portal、Usage、模型查询、Responses、SSE、401/404/429、超时/失败和重启。不能把真实用户请求同时发给新旧两套服务。
6. 演练逐账号配置挂载转换，以及发生在“Go 接流前”和“Go 已写入后”的两种回滚。

### B. 维护窗口内的执行顺序

| 顺序 | 动作 | 继续条件 |
| --- | --- | --- |
| 1 | 在 CPA 自有入口暂停新业务请求和 Admin/Portal 写入，保留现有 SSE 排空 | 新请求不再进入；旧在途数为零；超时未排空则中止或延长窗口，不直接杀流 |
| 2 | 停止旧调度、配额/切换/通知/清理任务；保留唯一旧 Collector 完成最后一轮 | 无额外生命周期修改；全部账号队列完成消费并成功入库 |
| 3 | 平滑停止 Collector、旧 Admin/Web/Gateway/Edge、旧 management 辅助容器和业务账号写入进程，阻止自动拉起 | 无剩余 SQLite/OAuth/config 写入；不影响 Caddy 证书和外部代理 |
| 4 | 生成最终备份与切换水位 `W0`，在同一停写窗口复制配对文件并验证 | 两库 `quick_check=ok`；可恢复清单完整；另一个故障域保存受保护副本 |
| 5 | 从最终备份再次转换，发布到原根目录；归档旧数据库和旧 WAL/SHM，禁止旧旁路文件配上新主库 | 两库转换完成、校验通过、配对密钥一致；恢复旧版本所需材料未覆盖 |
| 6 | 安装已验证发布元数据、准备新快照/目录；激活 Go 唯一所有权 | 旧 Python Writer 已实际停止；不能只依赖 Go lease 来约束旧进程 |
| 7 | 启动 Go 核心，按已演练步骤处理账号挂载并恢复运行状态；启动唯一 Collector 和必要 Writer | 每个账号原镜像/端口/有效配置一致且鉴权探测通过；快照新鲜；无重复消费者 |
| 8 | 在维护入口后使用原 Key 完成 API 与浏览器验收，再让 Caddy 转向 Go Edge并恢复业务 | 数据核对通过；真实模型、非流式和 SSE 通过；内部探测口仍不公开 |
| 9 | 恢复已批准的外部通知，核对发送水位；进入观察期 | 无补发风暴；新用量持续入库；旧进程保持停止 |

`W0` 不是单一时间戳：至少记录事件 ID/数量、自增序列、分块摘要、各用户额度基线和队列最后消费成功证据。最终排空不能只观察 `MAX(id)` 一次不变，也不能把一次短批次返回当作所有队列为空。

LPOP 有移除与持久化之间的故障空隙。切换时必须避免强杀消费者，并核对最后批次的提交；此方案以保留既有持久数据和经验证排空的新增数据为验收目标，不宣称当前队列协议具备任意崩溃下的端到端零丢失保证。

### C. Caddy 与端口切换

保留现有公网域名、TLS、Caddy 数据和 80/443。保留 Edge 原宿主机公开/内部端口；先停止旧 Edge 释放端口，再启动 Go Edge。本次跨语言 Edge 替换属于维护切换，不能直接等同 Go Gateway 内部蓝绿升级。

若 Caddy 目前通过 Docker 别名 `edge:8317` 访问旧 Edge，需要为 Caddy 与 Go Edge声明持久的专用入口网络，以唯一 Go 容器名/别名指定后端；旧业务网络保持不变。网络与 Caddy Compose 变更归入同一已审阅清单，避免仅执行一次 `docker network connect` 后重建丢失配置。

仅热加载 CPA 所属站点的后端变更，不安装 Nginx、不重新申请证书。若 Caddyfile 是单文件 bind mount，必须验证容器实际读取的是新内容，避免宿主机原子替换导致容器仍读旧 inode。新旧实例不可在同一网络同时提供相同 `edge`、`gateway-blue` 等别名。

### D. 时长与观察期

建议先预留 30 分钟维护窗口，最终按演练测得的备份/转换/恢复、逐账号探测及业务可接受的流式排空时间确定。长 SSE 可能显著延长排空，不能承诺固定秒级无感升级。

观察期至少覆盖连续 48 小时，并包含一个自然周边界或已完成等价跨周演练。保留旧镜像、数据库、配置和恢复清单；结束观察不代表自动删除备份。

## 6. 回滚设计

### Go 尚未产生新业务数据

停止 Go 所有 Writer/生命周期操作，恢复切换前两库及配对密钥、快照、配置和原部署文件。按清单恢复原账号容器挂载和 Image ID，恢复旧 Edge 和 Caddy 后端，再启动唯一旧 Writer并验收。

回滚账号挂载必须实际重建/探测，不能只把旧 YAML 文件复制回宿主机。OAuth 如果已经发生正常刷新，应保留最新有效文件并验证旧上游仍可读取，不能盲目用旧 refresh token 覆盖。

### Go 已经接收请求或发生业务写入

不能只恢复 `W0` 快照，否则会丢失切换后用量、额度动作、Key/账号修改和新 OAuth 状态。

使用原 Key 做 Responses/SSE 验收也会产生真实用量：即使公网仍处于维护状态，从第一笔此类请求开始也必须按本节处理，不能把“尚未向普通用户开放”当作“尚未写入”。

维护模式下再次排空并停写，保存 Go 的完整状态 `W1`。优先采用已经验证的旧版本兼容导出：在独立副本内投影回旧 Schema，按原 ID/event_key 保留新增用量、重新核对旧版聚合与额度，并映射所有用户/Key/路由/团队变更。保留两边的原始数据和新增数据归档，不把 Go Schema 原文件直接交给旧 Python 初始化器。

在反向转换没有完整演练前，自动快照回滚只能发生在第一笔真实业务写入之前。写入后失败保持维护并前向修复；不得以“快速回滚”为由丢弃新数据。因此，若要求真实验收或放流后仍能无损回到 Python，反向导出是上线前必做项。

## 7. 交付前的对抗式审查与验收门槛

| 最可能失败的点 | 必须拿到的证据 |
| --- | --- |
| Schema 版本号正确但额度语义改变 | 原字段摘要一致；个人额度跨周后仍保留；时区和历史加权口径一致 |
| 19 个或更多账号被统一镜像/默认配置重建 | 逐账号原 Image ID、端口和配置 diff；单文件转目录后原 Key 探测成功；回滚探测成功 |
| Caddy 或 Docker DNS 指到旧服务/两个服务 | 唯一后端和持久网络清单；重建后网络仍正确；真实公网请求命中新 Go 链路 |
| WAL、最后一批队列或 OAuth 写入遗漏 | 同一停写窗口、最终成功提交、完整备份、无遗留 Writer；恢复演练；不以两次在线单库备份冒充全系统同一时点 |
| 回滚丢失 Go 新增数据 | `W0 → W1 → 旧版恢复` 对账通过，覆盖事件、Key、额度和 OAuth；未通过则禁止放流后的自动数据回滚 |
