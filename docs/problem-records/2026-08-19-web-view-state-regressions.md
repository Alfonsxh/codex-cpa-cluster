# 2026-08-19 Web 分视图加载状态回归

- 状态：已修复，已于 cpa2 `v1.1.2` 部署验证
- 发现日期：2026-08-19
- 影响范围：管理中心的运行总览、系统设置、运行维护，以及跨页面刷新一致性
- 关联变更：`48b0595`（增加 Token 趋势）、`d9f12ba`（改为分视图加载和用户分页）

## 结论

页面加速本身是必要的，问题不在“分视图按需加载”，而在优化后仍有组件把别的页面状态当作自己的数据源。

`state.accounts` 只由账号管理页加载，`state.users` 只由用户管理页加载，`state.settings` 只由系统设置页加载。直接进入其他页面时，这些数组或对象仍是初始空值；如果先访问过对应页面，它们又可能只是旧快照或用户列表的当前一页。因此同一个操作会随访问顺序出现空列表、错误状态、遗漏影响范围或错误确认人数。

不要恢复旧的全量 `refreshAll()`。正确方向是让每个页面的 API 契约自包含，并显式维护跨页面失效关系。

## 根因与演进背景

`48b0595` 引入 Token 趋势时，管理中心每次刷新都会并发请求 `/overview`、`/accounts`、`/users`、`/settings`、镜像状态和 `/overview/usage`。在这个旧前提下，总览、运行维护和系统设置复用全局 `state.accounts`、`state.users` 是可工作的。

`d9f12ba` 为降低首屏成本，把刷新改为 `refreshView(view)`：

- 总览只请求 `/overview`，趋势另行请求 `/overview/usage`；
- 账号管理才请求 `/accounts`；
- 用户管理才请求分页 `/users` 和团队用量；
- 运行维护只请求 `/overview`；
- 系统设置只请求 `/settings`。

这次重构正确地缩小了网络和计算范围，但没有同步清理旧的跨页面消费者。之后的缓存、后台刷新、并发查询和静态资源优化只改变速度，没有制造上述数据依赖，因此不应通过回退这些优化解决问题。

关键代码证据：

- `admin/static/app.js`：`refreshView` 是页面状态的生产者；`monitorVariableConfig`、`monitorSeriesStatus`、`openUserQuotaAction`、`submitOperation` 是跨页面消费者。
- `admin/server.py`：`_load_overview_usage` 已读取完整账号和用户集合，却没有返回选择目录或状态；`settings` 已返回 `user_quota_operations` 全量汇总；`_account_operational_status` 是账号状态的服务端口径。
- `tests/test_portal.py` 当前主要验证脚本中存在特定标记，没有覆盖冷启动、访问顺序、分页目录和危险操作确认的行为，所以这类回归能够通过测试。

## 性能优化取舍

| 优化 | 结论 | 原因 / 调整方式 |
| --- | --- | --- |
| 分视图按需加载 | 保留 | 避免任何页面都拉取所有管理数据；修复页面数据契约，不恢复全量 `refreshAll()`。 |
| 用户服务端分页与按需详情 | 必须保留 | 数据复杂度从全量“用户 × CPA”矩阵降为“当前页摘要 + 单用户详情”。趋势选择目录另做只有 ID 和状态的 `/overview/catalog`，不能拿当前页冒充全量目录。 |
| 查询缓存、并发快照和后台额度刷新 | 保留并继续测量 | 这些优化和错误状态无直接因果关系；通过 `Server-Timing`、基准脚本和错误率决定 TTL，而不是凭感觉删除。 |
| 15 秒切页节流、30 秒自动刷新 | 有条件保留 | 只有补齐写操作后的依赖失效，节流才不会把已知旧数据继续展示。 |
| 页面间复用偶然存在的全局状态 | 删除 | 它不是有效缓存：没有所有权、完整性、版本或失效语义，且结果依赖访问顺序。 |
| Nginx 静态资源缓存 / gzip | 保留 | 与业务状态无关，收益明确。 |

2026-08-19 使用仓库基准脚本在临时数据上复测：1,000 用户、60 个 CPA、150,000 条事件时，分页摘要响应为 66,401 B，冷请求 158.28 ms，热请求 P95 11.09 ms，单用户详情 3.62 ms。结果说明分页和按需详情仍有明显价值；修复不应重新引入全量用户矩阵。

复测命令：

```bash
python3 scripts/benchmark_admin_response.py \
  --users 1000 \
  --accounts 60 \
  --events 150000 \
  --samples 5
```

## 修复顺序

1. 先修 WEB-STATE-003，避免危险操作的确认范围与真实范围不一致。
2. 为总览建立自包含的选择目录和状态契约，一次修复 WEB-STATE-001、WEB-STATE-002。
3. 为业务 CPA 停机补充实时影响信息，修复 WEB-STATE-004。
4. 引入领域级页面失效映射，修复 WEB-STATE-005，并接入账号、用户、团队、额度和配置写操作。
5. 增加行为测试后，再依据实际指标微调缓存 TTL；不把扩大请求范围作为兜底方案。

## 部署验证

- `v1.1.1` 首次部署后的附加检查发现，Admin 镜像中已有 `view-state-utils.js`，但 Web Nginx 的 `/admin` 静态资源白名单未包含该文件，导致公网请求返回 404；页面因此无法执行新的自包含状态逻辑。
- `v1.1.2` 将该资源加入精确白名单，没有扩大 `/admin` 的文件暴露范围；回归测试会从 Admin HTML 自动提取静态资源并逐项核对白名单，防止以后新增脚本时再次遗漏。
- 2026-08-19 在 cpa2 的运维方指定部署目录完成升级：公网 `/admin/view-state-utils.js`、`/admin/`、`/usage/` 均返回 200，两个新增 API 的未认证请求返回 401，`/__internal/snapshots` 继续返回 404。
- 升级前后账号数 17、用户路由数 240，数据连续性检查通过；Edge 和活动 Gateway 容器 ID 保持不变，数据平面未重启。
